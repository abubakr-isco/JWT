# Homework #40 — авторизация на JWT

Сайт с входом через [dummyjson.com](https://dummyjson.com): страница входа, защищённая страница профиля и выход.
Защищённые данные запрашиваются с заголовком `Authorization: Bearer <accessToken>`.

**Тестовый аккаунт:** `emilys` / `emilyspass`

## Запуск

Откройте `login.html` в браузере (лучше через Live Server в VS Code или `npx serve .`).

## Структура

```
login.html      — страница входа
profile.html    — защищённая страница профиля
css/style.css   — стили
js/auth.js      — общие функции: хранение токенов, выход, проверка ошибки авторизации
js/login.js     — валидация формы, POST /auth/login, сохранение токенов
js/profile.js   — проверка токена, GET /auth/me, обновление токена (refresh), выход
```

## Что сделано

| Задача | Где |
| --- | --- |
| 1. Форма входа, ошибки под пустыми полями, кнопка «Вход...» во время запроса, «Неверный логин или пароль» | `login.html`, `js/login.js` |
| 2. `accessToken` и `refreshToken` в `localStorage`, переход на профиль, редирект с `login.html`, если уже вошли | `js/auth.js`, `js/login.js` |
| 3. Без токена — на `login.html`; `GET /auth/me` с Bearer; фото, имя, email, возраст, город; «Загрузка...» | `profile.html`, `js/profile.js` |
| 4. 401 → удалить токены и выйти; кнопка «Выйти» | `js/auth.js`, `js/profile.js` |
| 5. ⭐ При 401 — `POST /auth/refresh`, сохранить новые токены, повторить запрос; не вышло — выход | `js/profile.js` |

### Как проверить выход при испорченном токене

DevTools → Application → Local Storage → поменять пару символов в `accessToken` → обновить страницу.
Приложение попробует обновить токен через `refreshToken`. Чтобы проверить именно выход, испортите оба токена
(или удалите `refreshToken`) — тогда откроется страница входа.

> **Особенность dummyjson.** На испорченный токен сервер часто отвечает не 401, а 500:
> испорчена подпись — `500 { "message": "invalid signature" }`, испорчена середина токена (payload) —
> `500 { "message": "Bad control character in string literal..." }`. Поэтому функция `isAuthError`
> в `js/auth.js` считает ошибкой авторизации 401, 403 и 500 — иначе ручная проверка из задачи 4 не сработала бы.
>
> Красная строка `Failed to load resource: the server responded with a status of 500` (или 401) в консоли
> при этой проверке — это сообщение самого браузера о неуспешном сетевом запросе, а не ошибка в коде:
> оно появляется у любого запроса с ответом 4xx/5xx, и убрать его из JavaScript нельзя.

## Ответы на вопросы

### 1. Из каких трёх частей состоит JWT и что хранится в каждой

JWT — это три части в формате Base64URL, разделённые точками: `header.payload.signature`.

1. **Header (заголовок)** — тип токена и алгоритм подписи, например `{ "alg": "HS256", "typ": "JWT" }`.
2. **Payload (полезная нагрузка)** — «claims», данные о пользователе и токене: `id`, `username`, `email`,
   а также служебные поля — `iat` (когда выдан), `exp` (когда истекает) и т. д.
3. **Signature (подпись)** — `HMACSHA256(base64url(header) + "." + base64url(payload), secret)`.
   Её может создать только сервер, знающий секретный ключ. По подписи сервер проверяет, что header и
   payload никто не изменил.

### 2. Почему в JWT нельзя хранить пароль

Payload **не зашифрован**, а только закодирован в Base64URL. Любой, у кого есть токен, может его
раскодировать (например, на jwt.io или через `atob()`) и прочитать содержимое. Подпись защищает от
**изменения** данных, но не от **чтения**. Токен к тому же хранится в браузере (`localStorage`), передаётся
в каждом запросе и может попасть в логи — значит, пароль утечёт. В JWT кладут только то, что не страшно
показать: id, имя, роль, срок действия.

### 3. Чем access-токен отличается от refresh-токена

| | Access-токен | Refresh-токен |
| --- | --- | --- |
| Зачем | Доступ к защищённым данным (`/auth/me` и т. п.) | Получение новой пары токенов (`/auth/refresh`) |
| Куда отправляется | В каждом запросе в заголовке `Authorization: Bearer ...` | Только на эндпоинт обновления |
| Срок жизни | Короткий (минуты — час) | Длинный (дни — недели) |

Access-токен живёт недолго: если его украдут, им можно пользоваться совсем недолго. Refresh-токен
позволяет не вводить логин и пароль заново каждый раз, когда access-токен истёк, — клиент молча получает новый.

### 4. Что означает ответ 401

`401 Unauthorized` — сервер не смог **аутентифицировать** запрос: токена нет, он истёк или недействителен.
Сервер как бы говорит: «я не знаю, кто вы». Правильная реакция клиента — попробовать обновить токен, а если
не получилось — разлогинить пользователя и отправить на страницу входа.

Не путать с `403 Forbidden`: там сервер знает, кто вы, но у вас нет прав на этот ресурс.
